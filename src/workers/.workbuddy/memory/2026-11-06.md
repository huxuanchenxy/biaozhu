## pdf_rename_inflate_upload.py 汇总计时口径（诊断结论，未改代码）

- 「各步骤累计耗时」是线程·秒：`_stats["t_dl"/"t_inf"/"t_ver"/"t_pu_s"/"t_pu_l"]` 由每个线程把单文件四段 wall time 直接 `+=`（约 1470-1473、1549-1553 行），在 `print_summary()`（约 2026-2043 行）打印；跨线程重叠累加，不是时间轴上真实经过的时间。
- 「总用时」是端到端墙钟：2339 行 `t_all = time.time()`（process_stream 起，含 HEAD 扫描）到 2346 行 `print_summary(args.apply, time.time() - t_all)`。并发 `ThreadPoolExecutor(max_workers=workers)`（1925 行）。
- 因此 `-w N` 时：累计 ≈ 墙钟 × N。实例（5.2_机械工程与制造 / 20261106090407 轮）：614 个 REPAIRED，累计 133m23.8s ÷ 墙钟 8m24.7s = 15.86 ≈ 16；逐文件 TSV 求和 133m26.7s 与累计吻合（差 2.9s 为 human_secs 取整）。
- 「平均 822ms/个」= 墙钟/614，是吞吐倒数，不是单文件耗时；单文件真实串行约 13.0s（下载 5.72 + 膨胀 0.022 + 校验 0.001 + 覆盖 7.30）。
- 已落地（用户确认后改）：`print_summary()` 内把 `ndone` 提前到 `if apply:` 开头，新增 `cum = sum(t_* 五项)`，并在「各步骤累计耗时」行后加一行口径说明（累计/总用时比值 ≈ 并发度、折算单文件耗时、两者不能相加）。刻意不改「各步骤累计耗时」标签文本、不改 `print_summary` 函数签名，避免影响已有日志解析与 2346/2390 两处调用。已通过 `py_compile` 及三种汇总模拟（真实一轮 / 0 完成项 / 干跑），真实一轮输出 `15.9×` 与 `13.0s`。

## 名单文件名含英文逗号导致未命中（已修）

- 现象：`orphans_5.2_机械工程与制造_成品语料.txt` 只剩一行 `Handbook of Mould, Tool and Die Repair Welding_sssss.pdf`，DRY-RUN 报「桶里既没有 Tool and Die Repair Welding.pdf…」。
- 根因：`entry_candidates()` 见逗号就按 CSV 切字段、只取以 `.pdf` 结尾的那个，文件名自带的英文逗号被当分隔符，`Handbook of Mould, ` 被丢掉。`load_files_from()` 保留整行是对的。
- 实锤：用完整 stem 对桶做只读 HEAD 能命中主件与 `_sssss`，`lookup_stem` 判为 `repair`（补做覆盖），不是文件坏了、也不是权限问题。
- 修复：`entry_candidates()` 改为多候选——整行以 `.pdf` 收尾且切完只有一个 `.pdf` 字段时，`raws=[整行, 老的 CSV 字段]`，`resolve_named_targets()` 里已有的 `for stem in entry_candidates()` 会先试整行、失败再回退；其它 CSV／表格行行为不变（少数情况多一次 HEAD）。`py_compile` + 10 种写法回归 + 完整 DRY-RUN 均通过，输出「计划：补做 1」。
- 环境坑：Git Bash 会把 `--prefix "/xxx"` 当 POSIX 路径转成 `E:/.../PortableGit/xxx`，复现时要 `MSYS2_ARG_CONV_EXCL='*' MSYS_NO_PATHCONV=1`；用户 cmd 环境无此问题。bash 里的 python 没装 PyMuPDF（校验降级为尾部指针），cmd 里的是内核口径。
- 仍存在的限制：`--files`（逗号分隔）不支持含逗号文件名，只能用 `--files-from`；多候选全未命中时报错显示的是最后一个候选的名字，有误导性，暂未改。
